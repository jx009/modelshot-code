# 模块切换性能排查（2026-10-01）

## 实测范围与结果

使用生产构建，通过 Chromium 实际点击导航并等待目标模块根节点可见。
线上测量地址为 `http://152.53.36.159:5000/zh`，使用未登录的新浏览器上下文；没有提交生成任务。

| 切换目标 | 当前线上 | 本地生产构建 |
| --- | ---: | ---: |
| 首页 → 电商套图 | 1397 ms | 112 ms |
| 电商 → 我的项目 | 853 ms | 70 ms |
| 我的项目 → 自由画布 | 1364 ms | 150 ms |

上述结果为单次诊断样本，不是 P95 或并发容量数据。两端版本、网络和服务环境不同，不应把差值直接当作代码优化收益。
本次线上访问记录到的首页 JavaScript 长任务为 52 ms，三个模块切换未新增超过 50 ms 的长任务。
独立 HTTP 请求测得连接约 275–283 ms、首字节约 567–614 ms；浏览器新上下文首页首字节约 1350 ms。
这支持继续优先改善资源等待和网络往返，不能据此排除登录后数据库、素材加载或大项目画布的性能问题。

## 代码问题与修复

- `15132ff` 已拆离客户端不需要的 Zod / 服务端校验依赖，缩小了页面依赖。
- 原主导航使用 `prefetch="auto"`，动态路由在点击前未取回完整页面；普通卡片禁用了预取。
- 新的 `NavigationLink` 默认按访问意图预取：鼠标进入或键盘聚焦时启用完整预取，避免所有可见卡片一起抢占连接；显式 `prefetch={false}` 仍保持关闭。
- 为语言路由增加轻量、适配主题的 loading 边界，路由结构已取回而页面仍在等待时显示骨架。路由结构尚未返回时，由既有导航状态提示反馈。

## 同环境前后对比

本地生产服务器，Chromium CDP 模拟 280 ms 网络延迟、512000 bytes/s 上下行；每组使用新的浏览器页面。
鼠标悬停组在点击前悬停 1200 ms，时间从点击开始计算，包含 Playwright 点击和页面可见性检查。

| 场景：进入电商套图 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 直接点击 | 889 ms | 890 ms |
| 提前悬停入口 | 841 ms | 74 ms |

请求记录确认修改后的完整页面请求在点击前发出。悬停不会消除下载耗时，而是将下载提前；直接点击仍需等待网络。
自动回归分别检查鼠标悬停和键盘聚焦、点击后复用已完成的请求，以及页面响应被阻塞时的加载状态。

## 验证边界

本地 UI 测试使用接口 fixtures，不需要数据库或模型凭据。线上这次没有登录状态，因此未验证私有项目数据加载、后台接口耗时或服务器负载。
发布本次修改后，仍需在实际登录账户和已有大项目上复测；不能用这里的本地数字承诺所有页面固定耗时。

## 第二轮：登录后的模块与重复请求

登录后通过内置浏览器打开了「我的项目」列表和已有的猫项目。列表正常返回已有项目；进入画布时先出现无模型的初始界面，再加载项目。此次没有获得登录接口的可靠耗时分解，不能把页面观察当作服务端性能测量，也没有提交付费生成。

代码与生产构建回归确认并修复了以下问题：

- 首页、灵感、案例、电商、项目和素材页各自挂载 `CreativeShell`。改为 `(creative)` 共享布局，URL 不变；页面等待时只替换内容区域，侧栏和顶栏保留。
- 画布默认模型请求完成后设置 provider，又触发第二次能力请求。改为单一请求流程，余额请求独立执行，切换模型仍重新加载对应能力。
- 能力 API 先解析配置再生成能力列表，重复读取模型和工具配置。现在单请求只读取各一次、并行执行；没有全局缓存配置，管理员改动在下一请求生效。
- 自动保存递增文档版本，重启已经结束的任务轮询。轮询改由项目、加载状态和新任务等事件驱动，不再依赖保存版本。
- 项目初次加载和分类切换无须等待搜索防抖；只对搜索文本防抖。素材分类查询不再跟随每次搜索执行。
- 灵感浏览页不查询未使用的模型列表。画布对话历史缩略图改为懒加载，减少与画布图片争抢下载连接。

验证：生产构建通过；`src` 和 UI 测试文件 ESLint 通过；相关供应商单元测试共 26 项通过；15 项生产 UI 测试通过。新增断言验证侧栏 DOM 在慢导航前后保持同一个节点、素材搜索不重复加载分类、灵感页无模型请求、画布模型只请求一次、余额请求被阻塞时模型仍可选择、自动保存不重启空任务列表查询。桌面和 390/320px、深浅主题截图回归通过。

这些是可验证的请求数量和布局生命周期改善，不是全站耗时降低比例。线上需要部署此轮提交后复测；大项目画布的帧耗时、真实素材吞吐和服务器并发容量仍未在本轮量化。

## 第三轮：案例与电商预览绘制

本地生产构建、1440×900、同一个 `quiet-living` 案例，通过拦截 Canvas 2D `drawImage` 计数对比：

| 首屏操作 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 初始绘图调用数（含预览复制） | 12 | 4 |
| 页面预览画布像素总量 | 3,883,500 | 866,972 |
| 点击复制前／后的累计绘图调用 | 12 → 24 | 4 → 4 |

原先六屏全部立即按导出分辨率绘制，复制按钮更新组件状态还会重建 brief 和分镜、导致全部重绘。现在只绘制视口附近内容，预览分辨率按显示宽度和像素比计算；相同输入返回视口复用已画好的内容。案例数据保持稳定，每屏单独记忆化。相同图片解码复用既有加载缓存。

商品展示和电商页面预览改用受权限保护的缩略图接口。导出与进入画布精修仍读取原图、使用平台原始分辨率。预览和导出共用版式计算，缩小预览不会改变文案换行逻辑。

新增 UI 测试逐屏滚动确认六屏可见时均绘制完成，并在 390px 屏幕编辑标题和版式后实际下载 ZIP，验证三种平台的整页输出分别为 750×5178、970×6696、1200×8280。绘图计数和像素量只代表这个预览场景的工作量，不代表全站加载速度提升比例。

本轮生产构建、改动文件 ESLint 和 19 项 UI 回归通过。期间预取测试的 `response.finished()` 对取消的 RSC 流出现挂起，改为等响应头和浏览器网络空闲，再验证点击复用及没有新增目标请求；键盘聚焦场景额外重复三次通过。
