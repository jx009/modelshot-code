## 部署必改项（代码层核实结论）

健鑫问"是不是只改 SMTP 就行"，逐项查过代码，结论是四项，不是一项：

1. `PUBLIC_URL`（映射 `NEXTAUTH_URL`）—— 不改会 403。`src/lib/http.js` 的 `sameOrigin()` 把 `NEXTAUTH_URL` 当期望 origin 和浏览器 origin 比对，不符抛 `CROSS_ORIGIN_REQUEST`；而 `readJson()` 会调用它，所以所有 POST 接口（注册、登录、提交生成）全挂。这是硬阻断。
2. `SMTP_HOST` + `SMTP_FROM` —— 注册链路必需，不是可选。`identitySchema`（`src/lib/domain/identity/verification.js:11`）里 `code` 强制 6 位数字，验证码经 `src/lib/email-service.js` 用 nodemailer 发送；不配 SMTP 无法注册 → 建不了 root → 后台进不去。`loadSmtpConfig` 的最低条件是 `host && (from || user)`，内网匿名 relay 可留空 user/pass；端口 465 才 `secure=true`，587 走 STARTTLS。
3. `BIND_ADDR` —— 默认 `127.0.0.1` 只能宿主机访问，必须挂反代；裸跑要改 `0.0.0.0`。
4. `TRUST_PROXY` —— 只有反代会覆盖 `X-Forwarded-For` 时才可 true，否则客户端能伪造，`clientAddress()` 采信后限流与审计 IP 失真。

留空不影响启动：`GOOGLE_*`、`OPENAI_API_KEY`/`GOOGLE_GEMINI_API_KEY`/`FASHN_API_KEY`、Stripe 三件套（配合 `PAYMENTS_ENABLED=0`）、`WEBHOOK_URL`、`PROVIDER_PROXY_HOSTS`、`QA_ENABLED`、`C2PA_ENABLED`。

已把这份必改清单写进 `docs/deployment.md` 的步骤 1 表格，并在 `.env.production` 对应行加了说明注释。

## SMTP 配置项行为（核实）

变量名是 `SMTP_USER` / `SMTP_FROM`，不是 `EMAIL_USER` / `EMAIL_FROM`，健鑫记错了名字，回答时要先纠正。

- **`SMTP_USER` 不能自定义**：是服务商签发的登录凭据。Gmail 填完整邮箱 + 应用专用密码；QQ/企业邮填完整邮箱 + 授权码；SendGrid 固定填字符串 `apikey`、密码填 API Key。
- **`SMTP_FROM` 的显示名随意，地址必须是服务商已验证的**：地址随意填会被严格服务商 550 拒发，宽松的能发出但 SPF/DKIM 对不上，大概率进垃圾箱。
- 代码强约束（`src/lib/email-service.js`）：`Boolean(user) !== Boolean(pass)` 直接抛 "Incomplete SMTP authentication configuration"，user/pass 必须成对；`from: from || user`，即 `SMTP_FROM` 留空会自动拿 `SMTP_USER` 当发件人；最低可用条件是 `host && (from || user)`。
- **读取顺序 DB > env**：`src/lib/site-config.js` 里 `getSiteConfig` 先查 `SystemConfig` 表（60s 缓存），DB 为空才回落 env。所以 SMTP / Google OAuth / Stripe 都能在管理后台改，且后台值优先于环境变量。
- 顺带发现：`getSiteConfig` 把含 **"待填"** 字样的 env 值视为未配置。我们模板里用的是"请替换为…"，不含该字样，所以不会被识别为未配置——如果想让占位符在漏填时表现得像未配置，措辞要含"待填"。

## SMTP_FROM 显示名自由度（nodemailer 实测）

用 `nodemailer.createTransport({streamTransport:true})` 跑真实 MIME 编译，结论：**显示名可以随便起**，认证只看域名。实测输出：

| 输入 From | 输出 From 头 |
| --- | --- |
| `ModelShot <no-reply@example.com>` | 原样 |
| `模特图小助手 <no-reply@…>` | 自动 MIME 编码 `=?UTF-8?B?…?=` |
| `ModelShot, Inc. <no-reply@…>` | 自动加引号 `"ModelShot, Inc."` |
| `ModelShot 官方客服 <no-reply@…>` | 编码后按 75 字符折行，地址保留 |
| `ModelShot "官方" <no-reply@…>` | 引号被当语法吞掉 → 变成 `ModelShot 官方` |

要点：中文、逗号、超长名 nodemailer 都会自动编码/折行/加引号，不用手动处理；唯一要避开的是显示名里写 `"`、`<`、`>`，会被当格式语法吞掉。显示名是纯展示项，改它不用重新部署（存 DB 或 env，DB 优先）。

留空安全，代码是防御性的：`src/lib/auth.js` 里

两项都填才注册 Google provider。`src/app/[locale]/login/page.js` 用 `getProviders()` 判断，没有 google 就 `setActiveTab("email")` 并把 Google 按钮 `disabled`。所以留空 = 只有邮箱登录，页面不会报错。

```ini

```

关键推理：`PUBLIC_URL` 必须和浏览器地址栏 origin 完全一致（含端口），所以 IP 方案下写成 `http://IP:3000`，同时 `BIND_ADDR=0.0.0.0`（否则外网访问不到，且需放通安全组 3000），`TRUST_PROXY=false`（无反代）。

## 镜像来源：MODELSHOT_IMAGE 与 Docker Hub 实况

## 排障：send-code 报 INTERNAL_ERROR / type:"Error"

现象：点击「发送验证码」→ 容器日志出现 `{"traceId":"...","code":"INTERNAL_ERROR","type":"Error"}`。健鑫称已在 `.env` 和 `.env.production` 都填了 SMTP_PASS，重建后仍复现（新 traceId `023a9206-...`）。

**日志机制**：`src/lib/http.js` 的 `errorResponse()` 只在 `!(error instanceof AppError)` 时 `console.error({traceId, code:"INTERNAL_ERROR", type:error.name})`，**不打堆栈**（项目设计上排障不输出密钥/原图/提示词）。已知业务错误走 AppError，不打日志。所以 `type:"Error"` = 普通 Error 未预期异常。**定位手段：traceId 会原样出现在响应体里，可在浏览器 Network 面板按 traceId 反查是哪个接口。**

`POST /api/auth/email/send-code` 的执行顺序（`src/app/api/auth/email/send-code/route.js`）：
1. `readJson`（含 sameOrigin）
2. `rateLimit` —— 走 **数据库**（不是 Redis，`src/lib/domain/identity/rate-limit.js` 用 `db.rateLimit.upsert`），只抛 AppError
3. `issueChallenge` ← **先于发信执行**
4. `sendVerificationEmail`

**关键更正**：我之前猜是 SMTP，但第 3 步就可能是元凶。`verification.js:16-19` 的 `digest()`：

```js
const key = process.env[`VERIFICATION_KEY_${record.keyVersion}`] || (record.keyVersion === "1" ? process.env.NEXTAUTH_SECRET : null);
if (!key || key.length < 32) throw new Error("Verification key unavailable");
```

`keyVersion` 取自 `VERIFICATION_KEY_VERSION || "1"`。我们 env 里 `VERIFICATION_KEY_VERSION=1`，所以回落 `NEXTAUTH_SECRET`；**若容器内 `NEXTAUTH_SECRET` 缺失或长度 < 32，这里直接抛普通 Error**，正好是 `type:"Error"`。

**首要假设**：服务器上的 `.env.production` 若从 `.env.production.example` 复制而来，`NEXTAUTH_SECRET` 仍是占位符 `请替换为openssl-rand-hex-32`（JS 字符串长度 22 < 32）→ 必然抛此错。该假设能完整解释现象：页面能打开、能点发送验证码（都不依赖密钥）、一点就报错。

已给出两条诊断命令：① 打印各密钥的**长度/格式**（不打印明文，避免泄露）；② 在容器内直接 `import { issueChallenge } from "./src/lib/domain/identity/verification.js"` 复现并打印真实错误名 + 堆栈——这是绕过应用吞异常、拿到真相的最短路径。等健鑫回传输出。

## 供应商 baseURL / 中转站配置（代码核实）

健鑫问「中转站 URL 要不要填 v1」。结论：**要填**。

依据：
- `src/lib/ai/adapters/openai.js` 用官方 SDK：`new OpenAI({ apiKey, ...(config.baseURL ? {baseURL} : {}) })`，未传 baseURL 时用 SDK 默认值 `https://api.openai.com/v1`（见 `node_modules/openai/client.mjs:195`）。
- SDK 的 `buildURL()`（`client.mjs:435-439`）是 `baseURL + path` 直接拼接（仅当 baseURL 以 `/` 结尾且 path 以 `/` 开头时去掉 path 的首个 `/`，避免 `//`）。
- 调用的是 `this.client.images.edit()` → 路径为相对路径 `/images/edits`（`node_modules/openai/resources/images.mjs:22`，multipart）。

所以：`https://中转站/v1` ✓ ；`https://中转站/v1/` 也 ✓（尾斜杠被 SDK 处理）；`https://中转站` ✗（会请求 `https://中转站/images/edits` → 404）。

**两个必踩的坑**：
1. **`PROVIDER_PROXY_HOSTS` 白名单**。`src/app/api/admin/providers/route.js:56-60`：只要 `input.baseURL` 非空，就要求 `https:` 协议、无 username/password/query/hash，且 `url.hostname` 必须在 `PROVIDER_PROXY_HOSTS`（逗号分隔）里，否则抛 `PROVIDER_PROXY_NOT_ALLOWED`。只比对 hostname（不含端口），所以填主机名即可。这是防 SSRF 的设计。改这个变量需要 `--force-recreate`。
2. **中转站必须支持 `/v1/images/edits`（multipart）**。项目走的是图像编辑接口而非 chat/completions，很多只代理 chat 的中转站会 404。选站前必须确认。

另外：模型名可在后台「模型」字段覆盖（代码注释举例中转站自定义名 `gpt-4o-image-vip`），留空默认 `gpt-image-2`。管理后台有「测试连接」，会做 dry-run + 真实 1x1 图验证 key/baseURL/model 全链路。

已把 `PROVIDER_PROXY_HOSTS` 的填写要求与 `PROVIDER_PROXY_NOT_ALLOWED` 报错原因写进 `.env.production` 注释。

## 502 Bad Gateway 是本地 Clash 代理造成的

健鑫反馈「测试连接」失败，浏览器 Network 显示：`POST http://152.53.36.159:5000/api/admin/providers` → **502**，**远程地址 `127.0.0.1:7890`**。

**结论：不是服务器问题，请求根本没到达服务器。** `127.0.0.1:7890` 是 Clash / Clash Verge / Mihomo 的默认混合代理端口——浏览器把请求交给本地代理，代理转发失败直接回 502。服务器是德国 Contabo IP，Clash 规则通常把境外 IP 走代理节点，节点连不通即 502。

给出的排查与修法：`curl --noproxy '*' -s -o /dev/null -w '%{http_code}\n' http://152.53.36.159:5000/api/health` 验证绕过代理后是否 200；修法为临时关闭系统代理，或在 Clash 规则最前面加 `- IP-CIDR,152.53.36.159/32,DIRECT`，或把该 IP 加入系统代理例外。

**顺带核实的一个重要行为**：`POST /api/admin/providers`（测试连接）只接收 `{ id }`，配置从数据库读取（`prisma.modelProvider.findUnique`），**不接受请求体里的 baseURL/apiKey**。所以必须先「保存配置」成功，测试才有意义。而保存当前被两件事挡着：① 上面的代理 502；② `crypto.randomUUID` 修复尚未部署（因 push 未完成）。

**已证实**：健鑫执行 `curl --noproxy '*' ... http://152.53.36.159:5000/api/health` 返回 **200**，确认服务器健康、502 由本地 Clash 代理造成。

**注意这是一个间歇性故障**：他此前能正常注册、登录、进后台，说明代理并非始终拦截该 IP——更可能是 Clash 的 URL-test 节点组把这条流量切到了不通的节点。因此根治手段是加 `IP-CIDR,152.53.36.159/32,DIRECT` 直连规则，而非依赖节点可用性。另：他的 shell 是 Windows CMD（提示符 `C:\Users\17519>`），单引号不是引号字符，给命令时要用双引号。

**沟通教训**：我写「你用的哪个 Clash 客户端」被健鑫反问「一个 web 测试请求居然受限于我本地电脑环境？」。问题是两点：① 没说清楚「不是测试请求特殊，而是你访问该站点的所有请求都先经过 Clash 系统代理」这条链路；② 用「哪个客户端」这种含糊说法，应该直接说产品名 Clash 并解释它有多个发行版（Verge / for Windows / Mihomo Party / ClashX）导致菜单位置不同。**给非全栈用户解释代理问题时，先画链路（浏览器 → Clash → 目标），再讲操作。**

**二次反驳与最终解释框架**：健鑫强烈质疑「公网 web 的测试连接怎么会受我本地影响，不应该走服务器自己的网络吗」。他说的**是对的**——但只对第二跳。正解：**「测试连接」是两次网络请求**，必须分开讲：

- ① 浏览器 → 你的服务器（`POST /api/admin/providers`，带 session cookie 与 provider id）——**这一跳走浏览器所在网络，502 就发生在这里**
- ② 你的服务器 → 中转站（服务器读数据库里的配置去调用）——这一跳走服务器网络，他的判断正确

并需澄清「公网」的含义：公网指的是**服务器端可被任何人访问**，不代表「客户端 → 服务器」这段路不受客户端网络影响（访问 google.com 的请求同样先从本机经过代理）。**结论：讲这类问题时必须按「网络跳数」拆开，不能笼统说「测试连接走哪边」——这是同一个操作里跨越了两种网络路径。**

**给他的自证实验**（避免陷入各说各话）：a) DevTools 的「远程地址」是浏览器自己填的 socket 对端，直连时应为 `152.53.36.159:5000`；b) 手机开移动数据（不经本机代理）访问 `http://152.53.36.159:5000`，能打开即证明服务器公网可达；c) 关掉 Clash 系统代理再点测试连接，若不再 502 即闭环。

**三次反驳与措辞修正（重要）**：健鑫第三次反驳是「我发布一个网站，然后我这个网站还不让用户开代理了？扯淡呢」。这句本身**完全正确**——网站不该要求用户关代理。问题在于我的表达让他把两件事混成一件：

- ❌「网站要求用户不开代理」——荒谬，不成立，也不是我的主张
- ✅「他这一台 Clash 的规则把去该 IP 的流量指给了不通的节点」——是那套代理配置的路由问题，跟网站无关

**必须建立的区分：代理配置出错 ≠ 网站加的限制。** 全世界大量用户开着代理访问各类网站都正常；代理配置正确时访问本项目同样正常。类比：导航把你导到封路巷子，不等于「这条街不让开车」——是导航的路线数据有问题。

另一个措辞教训：我提的「关掉系统代理」只是**定位故障的临时手段**（类似牙疼先别吃糖以确认病因），不是解决方案，更不是网站的要求；必须显式说明，否则会被读成「以后都不许开代理」。

**顺带发现的真实产品问题（值得他现在决定）**：服务器是德国 Contabo IP。① 国内用户直连德国 RTT 明显偏高；② 国内用户的代理软件普遍把德国 IP 归类为「境外流量」，从而走代理节点——这也是他自己撞上这个问题的原因。若目标用户是国内电商卖家，香港/国内节点会显著更好。
