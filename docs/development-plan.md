版本：2026-09-11。方案范围已实施，最终开发验收记录见 `docs/development-progress.md` 与 `docs/release-acceptance.md`；真实环境验收按第 13 节延期。

## 1. 目标与判断

ModelShot 定位为面向电商服装卖家、服装品牌及摄影工作室的 AI 模特上身图生产工具。首版重点服务需要持续上新 SKU 的中小服装商家，核心流程为：上传服装素材 → 配置模特、场景和输出规格 → 单张或批量生成 → 检查服装细节 → 筛选、导出、再次复用。

当前已有可继续演进的应用基础、生成适配层、计费数据结构和工作台界面，但仍有会影响用户资产、扣费准确性、任务恢复和结果交付的问题。目前不能据此认定为优质生产级项目。功能合格也不能只按页面或按钮数量判断，应检查上述流程在成功、失败、重复操作、进程重启时是否都能完成。

本轮开发目标是形成“可在本地完整验收、具备上线准备条件的 V1 候选版本”。真实供应商出图质量、支付与邮件真实联调、部署运行等验收延期。因此完成本方案后，仍不能直接宣布已经达到真实生产可用或可商用、可过审的效果承诺。

建议产品边界：

- V1 必须完成：素材归属、草稿与 SKU 分组、有效参数配置、可靠任务和计费、结果检查、失败恢复、批量导出、账户账单、必要管理能力。
- V1.1 再做：局部重绘、复杂多角度套图、固定模特身份库、团队协作、跨平台商品刊登、更多供应商和高级自动审核。
- 已有分销功能需要保证金额、退款和结算正确；新增营销玩法不作为 V1 前置条件。
- 暂不重写技术栈，不引入微服务拆分，不把全量 TypeScript 迁移作为前置工作。

## 3. 技术路线与模块边界

保留 Next.js / React / next-intl / Prisma / PostgreSQL。采用模块化单体加独立 Worker，使用已有 BullMQ、Redis 依赖承载队列。PostgreSQL 是任务和账务事实来源，Redis 队列负责调度，可由数据库重建。

```text
工作台 / 图库 / 账户 / 管理后台
              |
        Next.js API
        鉴权、输入校验、报价、业务事务
              |
        PostgreSQL
        素材、任务、预留、流水、事件、Outbox
              |
        Outbox Dispatcher -> BullMQ / Redis -> Worker
                                                |
                                      Provider Adapter
                                                |
                                     私有对象存储 / 导出

支付入口 -> 签名校验 -> 持久事件收件箱 -> 账务与订阅处理
独立对账任务 -> 未知任务、未处理事件、过期预留、孤立对象
```

建议逐步整理到 `src/lib/domain/{assets,generation,billing,identity}`、`src/lib/infra/{queue,storage,providers}` 和 `src/workers/`。API 负责鉴权和协议转换，领域服务处理业务事务；不要为了目录美观搬迁无关模块。

接口输入、供应商响应、配置快照和队列载荷引入运行时 schema 校验，可选 Zod。新增复杂边界可以使用 TypeScript，保留现有 JSX 组件。Worker 只携带内部 ID 和版本，不携带明文密钥或长期依赖会过期的签名 URL。

本地环境提供 PostgreSQL、Redis、一个 S3 兼容对象存储和邮件捕获服务；供应商用可编排的 Fake Adapter。生产首版只选定一个 S3 兼容后端实现，不同时开发多套云厂商专用实现。

## 4. 必须先固定的业务规则

### 4.1 账户、权限与素材

- 使用邮箱或 OAuth 建立身份。用户身份与供应商密钥完全分离。
- 供应商密钥只允许管理员配置，使用带密钥版本的认证加密；会话、日志和用户接口不返回密钥。Worker 按需在服务端解密。
- 管理操作在服务端校验角色、作用范围和账户状态。封禁和改密时按策略撤销会话；敏感操作遇到权限存储故障应拒绝执行。
- 邮箱验证码使用带服务端密钥的摘要，按邮箱/IP 限流，设置尝试次数、有效期和原子单次消费；生产禁止返回调试验证码。
- 所有素材、任务、账单、导出和项目接口验证所有权，管理员特权访问有审计记录。
- 上传验证体积、实际文件类型、可解码性、像素上限，并规范化重编码；服务端不接受客户端传来的任意本地文件路径。
- 需要外部图片导入时，校验目标地址、重定向和实际连接地址，阻断内网、回环及元数据服务，限制时间和响应大小；供应商返回的下载 URL 同样受控。

### 4.2 报价、额度与扣费

首版采用“提交时预留，产物成功交付时确认消费，无可交付产物时释放”的统一模型。用户可用余额等于已入账余额减有效预留，预留不能被其他任务重复使用。

- 服务端生成报价快照：计价版本、积分/额度来源、单价、张数、币种或积分单位、有效期和配置摘要。前端展示预估，提交前确认服务端报价。
- 同一提交包含 N 张时，在一个数据库事务中校验报价、创建 N 个子任务、预留全部资源并写入 Outbox。余额不足或任一校验失败时整单不成立。
- 预留按输出项分配；每个输出明确关联 reservationId 和原始消费流水 ID。禁止“找最近一笔未关联消费”补关联。
- 消费确认、预留释放及已消费退款均有数据库唯一业务键和条件状态变更。积分流水与余额更新在同一事务完成。
- 一个输出只能确认一次消费；释放不能同时确认。已确认后需要退款时写补偿流水，关联原消费，禁止覆盖历史流水。
- 技术自动重试属于同一个输出，不额外扣用户费用；已失败并释放资源后的用户手动重试创建新任务和新报价。用户主动重新生成也是新消费。
- 已持久保存、可授权读取的原始生成图视为可交付。QA 的待检查、跳过或错误不自动退款，需在费用规则中明确；没有有效图片不能当作成功。
- 导出衍生图、QA 或元数据处理失败，应允许针对该步骤重试，避免再次生成和重复扣费。V1 默认基础导出与技术重试不单独收费。
- 排队取消且未调用供应商时立即释放。运行中尽力取消：确认无产物后释放；若已完成或无法取消并交付成功则正常确认消费，页面须告知取消结果。
- 供应商结果未知时进入对账并保留预留，配置明确的对账期限。期限到仍无法确认交付则关闭本次交付并释放，后到产物隔离供审计，不追扣用户；潜在供应商费用由平台承担并报警。
- 免费月额度采用明确的 UTC 自然月；付费订阅额度按实际计费周期。每次占用、消费和释放记录 cycleId，跨期退款归还原周期，过期周期不增加本期额度。
- 单张与批量统一使用管理员配置的平台供应商，报价只使用套餐额度和积分两种渠道。
- 每个供应商的管理员密钥独立保存，禁止将某厂商密钥发送给其他厂商。

### 4.3 任务、取消与恢复

建议生成状态为 `queued → running → provider_pending → succeeded / failed`，另有 `reconciling`、`cancel_requested`、`cancelled`。供应商同步返回时可跳过 provider_pending。QA、导出、元数据各有独立处理状态，避免把“图已生成但待检查”当作生成失败。

- 每次执行保存 attemptId、供应商请求 ID、租约截止时间、心跳和递增 fencing token。过期执行者的回写必须被数据库条件更新拒绝。
- 终态不可被旧 Worker 覆盖。完成任务、确认消费、登记后处理 Outbox 必须协调为同一数据库事务。
- 入队允许至少一次投递；消费者靠数据库约束和状态条件实现业务副作用幂等，不能宣称外部生成天然“恰好一次”。
- 对超时、限流、明确无效输入、鉴权失败分别制定重试规则。有供应商幂等键时使用，没有时遇到提交结果不明先查询对账，不盲目重新提交或跨厂商切换。
- 原图上传成功而数据库提交失败时，使用稳定对象键与输出记录核对，避免重新生成；定期清理无引用对象。
- 批次聚合显示 queued/running/succeeded/partial_success/failed/cancelled。全部失败必须为 failed，部分取消与失败展示真实数量，不通过重复自增作为唯一统计依据。
- 读取列表不修改任务或资金。超时扫描、租约恢复和财务对账由独立计划任务执行。
- 刷新页面、重新登录或 Worker 重启后通过任务 ID 恢复进度；轮询需有退避和停止条件，V1 不强制引入 WebSocket。

## 5. 数据与接口设计

以下是逻辑模型，可通过扩展已有 TryOn、BatchJob、CreditTransaction、Order 实现，避免建立两套并存的任务或账务事实来源。

| 模型 | 关键内容与约束 |
| --- | --- |
| Project / Draft / Garment | 所属用户、SKU、名称、归档状态、草稿版本、引用素材；先做单用户归组 |
| Asset / AssetDerivative | ownerId、对象键、用途、实际 MIME、尺寸、checksum、状态、来源和版本；原图不可变 |
| ModelProvider | provider、管理员加密密钥、Base URL、模型、优先级与启停状态；不进入用户会话 |
| GenerationJob / Output | 批次关系、SKU、配置快照、状态、输出素材、幂等键、错误码、版本 |
| GenerationAttempt | 输出 ID、执行版本、provider/model、requestId、lease、开始结束、错误、预估及实际成本 |
| CreditReservation / Ledger | 每输出预留与状态、sourceTransactionId、cycleId、幂等业务键；积分与真实货币分别建模 |
| BillingCycle / Subscription | 起止时间、权益快照、状态、Stripe customer/subscription ID、同步版本 |
| Order / PaymentEvent | 货币最小单位整数、currency、session/invoice/payment ID；eventId 唯一，权益发放另有业务唯一键 |
| OutboxEvent | 事务内持久化、事件类型、实体 ID、投递状态、失败次数；可重放 |
| QualityReview / ExportJob | 独立状态、schema 版本、报告或导出对象、固定选择集合、有效期 |

原始配置快照至少包含 garmentType、素材及版本、模特/场景快照、模板版本、补充提示词、pose/camera/lighting、provider/model/能力版本、允许的 fallback、生成尺寸和交付规格、报价版本。记录随机种子只在供应商支持时启用；可复用配置不等于像素级确定性复现。

建议统一错误响应为 `{code, message, retryable, traceId, fieldErrors?}`。错误文本本地化，客户端依据稳定 code 处理。写请求携带客户端幂等键，服务端按用户与操作作用域去重；相同键但不同参数摘要应返回冲突。数据库有唯一约束，不能只靠客户端防抖。

建议 API 合同如下，可先通过现有路由适配，不要求一次性更名：

| 接口 | 合同 |
| --- | --- |
| 上传/确认素材 | 校验上传内容后返回 owned assetId；直传需要上传意图、短期签名和服务端完成校验 |
| 保存/读取草稿 | 带版本更新，冲突时保留用户内容，支持 SKU 归组 |
| 获取报价 | 校验能力、素材与数量，返回 quoteId、费用分解和有效期 |
| 提交任务 | quoteId + 配置摘要 + Idempotency-Key；成功返回任务 ID 和实际预留 |
| 查询/取消/重试 | 查询无副作用；取消返回实际状态；失败项重试返回新任务关联 |
| 图库列表 | 服务端按归属、项目/SKU、批次、状态筛选及游标分页 |
| 导出任务 | 固定 owned outputIds 和规格快照；异步进度、失败清单、到期下载 |
| 支付 webhook | 原始请求体签名验证；持久化事件成功后应答，异步处理可重试 |

限制应集中配置并被 UI 和服务端共同使用：每张图片字节/像素、每批服装数、每件变体数、每批总输出数、用户并发、队列容量和导出体积。保留当前“最多 50 件”的意图时，必须同时计算变体乘积并在提交前展示总图数与费用；不能只限制上传文件数量。

## 6. AI、质量检查与交付

### 6.1 参数真实生效

建立按 provider/model/version 的能力表：输入类型、服装类型、模特参考、场景参考、姿态控制、尺寸、最大输出、异步查询及取消支持。UI 控件从相同能力数据读取，服务端再次验证。

FASHN 等专用试衣接口仅开放实际支持的控制，素材转换为该接口接受的安全引用；不能把公开目录相对路径直接当外部可读 URL。没有启用任何供应商时明确不可提交，不回退到默认隐藏供应商。

提示词由结构化意图与版本化模板构建，自定义文本默认是补充。高级完整替换需要明确模式，避免用户改姿态却继续复用旧的完整提示词。Fallback 只能选择满足同一请求能力的模型，必要降级需在提交前明确。

### 6.2 输出尺寸与图像资产

原生生成尺寸与交付尺寸分开。当前将 3:4、9:16 等映射到统一尺寸不代表最终满足比例。建立版本化输出 profile，使用图像处理生成精确像素尺寸的衍生图。

默认等比完整保留服装，可补边；用户选裁切时提供预览并保存裁切参数，禁止拉伸。实际 MIME 与扩展名一致，不把 JPEG 字节直接命名为 PNG。保留原始生成图，衍生图以新版本存储。

QA 状态为 `pending/passed/needs_review/skipped/error`，人工决定另存 approved/rejected。缺图、跳过和服务错误不得给出伪合格分数；报告校验严格 schema，展示判断依据。用户可对比原服装的颜色、版型、图案和关键细节，但自动分数不等于商业真实性保证。

EXIF/IPTC 在图像转换后注入，C2PA 如启用则最后签名，所有后续再编辑需要重新签名。未配置有效签名能力时标明未签名，不使用测试证书冒充生产信任。平台规格只描述像素/格式要求，不承诺审核一定通过或自动获得商业使用权。

## 7. 支付、订阅和管理闭环

- 统一价格目录作为定价页、Checkout、订单和权益快照来源。真实货币使用 amountMinor 整数及 currency，按币种指数展示；积分单独计量。
- Stripe 事件落库后处理，eventId 防事件重放，session/invoice 等业务唯一键防不同事件重复发同一权益。
- 支付完成按实际支付状态判断，覆盖延迟支付成功/失败。续费按 invoice 和订阅实际周期发权益，不使用“当前时间加 30 天”。
- 保存 customerId、subscriptionId，显式设置需要的 metadata；乱序事件通过拉取或事件快照版本协调，避免旧取消/更新覆盖较新状态。
- 明确取消到期、欠费宽限、续费失败、套餐升级和降级政策。建议 V1 变更套餐下周期生效，不先做复杂按比例即时换算。
- 接通退款与争议状态。部分退款关联原支付并限制累计金额，积分包退款回收未使用权益；已消耗权益转人工审核，不能扣成静默负余额。
- 佣金按实际已结算净额和比例快照计算，金额按明确舍入规则存最小货币单位；退款按比例冲回，已结算佣金记调整项而非抹除结算历史。
- 管理后台提供订单、流水、任务、异常和审计检索；手动补偿需要原因、明确对象、幂等标识和操作日志。保留现有角色体系并做权限矩阵，V1 不建设复杂自定义 RBAC。
- 用户账户页提供可用/预留/已消费额度、计费周期、流水、订单、票据链接和订阅取消入口。取消、退款与生成失败三种结果不能共用含糊提示。

## 8. 前端升级范围

整体风格保持服装生产工具的清晰、紧凑和可扫描性，基于现有工作台迭代。首屏继续进入实际工作流程。

## 9. 实施阶段、依赖与交付

工期按一名熟悉该技术栈的全职工程师估算，单位为有效工作日，包含对应阶段的测试及修复。它是范围估算，不是固定交付承诺；真实环境验收不计入。

| 阶段 | 工作范围 | 可检查的交付物 | 开发验收 | 预计 |
| --- | --- | --- | --- | --- |
| M0 基线 | 固定 Node/包管理器与锁文件；清理全量 lint；本地服务、测试框架、假供应商、CI；记录依赖风险 | 环境说明、启动脚本、CI、测试夹具、基线报告 | 干净安装、构建和静态检查可重复；现有行为有记录 | 3–4 天 |

| M2 可靠生成纵向闭环 | 统一报价预留；单张和批次子任务；Outbox/Worker；租约、重试、取消、对账 | 一条从素材到交付再到账本的完整链路、故障测试 | 重复请求不重复扣费；重启可恢复；部分失败资金正确 | 8–12 天 |
| M3 参数与交付 | 能力表、配置快照、模板、输出尺寸、QA 分离、异步导出 | 能力矩阵、交付 profile、QA 报告、导出任务 | 支持的参数可追踪；尺寸准确；后处理重试不重新生成 | 4–6 天 |
| M4 商业闭环 | 价格目录、webhook、续费/取消、退款、佣金和账单 | 事件处理器、对账工具、账户账单、金额迁移报告 | 签名模拟事件重放/乱序、周期和退款测试通过 | 5–8 天 |
| M5 前端工作流 | 草稿/SKU、工作台恢复、图库分页选择、详情、移动端、管理入口 | 可完整操作的 V1 页面和浏览器回归 | 登录后从上传到下载及异常恢复走通 | 5–8 天 |
| M6 发布准备 | 综合故障回归、日志指标、迁移演练、文档、遗留问题收口 | 开发验收报告、部署/恢复手册、真实验收清单 | 本地验收门槛全通过，剩余项明确标为延期 | 3–5 天 |

合计约 33–50 个工作日；按数据迁移复杂度预留约 20% 缓冲，整体约 8–12 周。若无有效历史数据，迁移工作会减少；若旧账务混杂且需人工核对，则重新估算。多人实施必须先稳定契约，不机械按人数折算工期。

依赖顺序：M0 → M1 → M2；M3 和 M4 依赖 M2 的任务与账务合同；M5 的接口准备可提前，但完整验收依赖 M3/M4；M6 最后汇总。每阶段的测试随实现提交，不拖到 M6。商业支付在 M4 通过前保持禁用，P0 问题解决前不扩大对外使用。

建议单个工作包控制在 1–3 天，每包包含数据/API 改动、必要 UI 接线、测试和简短说明。跨包迁移使用兼容步骤，避免一个超大 PR 同时改完所有模块。

## 10. 本地验收方案

本方案跳过的是真实环境验收，不跳过本地功能、并发和故障验收。使用真实本地 PostgreSQL、Redis、S3 兼容服务验证事务和存储；SQLite 或内存 mock 不能证明 PostgreSQL 锁与约束正确。

| 验证类别 | 必测场景 | 判定依据 |
| --- | --- | --- |
| 身份与权限 | 同后缀密钥、跨用户 asset/job/export ID、封禁与改密后旧会话、越权管理动作 | 无身份混淆、无跨用户读取/修改、拒绝后无副作用 |
| 输入与凭据 | 路径穿越、内网 URL/重定向、伪 MIME、超大像素、日志/会话和客户端 bundle | 拒绝恶意输入；密钥不出现在返回、日志和前端 |
| 并发额度 | 余额仅够一单时 20 个并发提交；一单 N 张余额不足；同幂等键并发 | 无超额预留，整单原子，恰当去重或冲突 |
| 退款与周期 | 重复消费确认/释放/退款，跨月、订阅实际周期、已消费部分退款 | 守恒、无重复变动，周期归属正确，可完整追溯 |
| 调度故障 | DB 提交后入队失败，重复消息，Worker 中断，租约过期，旧 Worker 晚回写 | 任务可恢复，旧执行者不能改变新状态和财务 |
| 外部不确定性 | 提交后丢响应，供应商迟到结果，无幂等/查询支持，取消竞争 | 进入对账；无盲目重复调用；期限后按政策关闭并释放 |
| 文件与后处理 | 上传成功后 DB 失败、无效输出字节、QA 服务故障、导出中断 | 不丢已交付原图，步骤可独立恢复，孤立对象可清理 |
| 参数和 QA | 各能力允许/拒绝组合，输出比例、补边/裁切，QA 缺图/跳过/错误 | UI 与服务端一致；像素精确；未知结果不伪报通过 |
| 支付 | 使用测试密钥对 fixture 签名；无效签名、重复和乱序事件、续费/取消/退款/争议 | 无重复发权益，金额币种正确，异常事件可重试 |
| 浏览器流程 | 登录夹具、草稿、上传、单张/批量、刷新、取消、重试、分页、下载、账单 | 桌面/移动完整操作；下载文件内容有效；控制台无阻断错误 |
| 迁移恢复 | 合成旧数据、同后缀账户、历史金额混用、处理中任务、部分迁移失败 | 预检识别冲突，回填幂等，迁移前后数量/余额核对一致 |

测试分层建议：Vitest 进行纯函数和服务测试，数据库集成测试使用隔离测试库，Playwright 做登录后的端到端流程。测试认证仅限测试环境，通过正常测试账户或隔离夹具建立，不在生产增加绕过鉴权入口。

Fake Provider 至少支持成功、明确失败、限流、超时、请求已受理但响应丢失、延迟完成、无效图片和后处理失败。使用合法测试图片和可控时钟，不依赖外部付费调用。

已实现命令：`npm run test:unit`、`npm run test:integration`、`npm run test:e2e`、`npm run worker`、`npm run test:acceptance`；另有恢复、容量和依赖扫描命令，见 README。

开发完成门槛：

1. 干净环境安装与构建成功，全量 lint 无错误，design/i18n 检查通过；警告逐项解释或修复。
2. P0/P1 范围的关键测试通过，无未解释的跳过；测试报告记录环境、提交版本、场景和结果。
3. 依赖漏洞逐项确认可达性与影响，修复实际可利用的高风险问题，避免盲目强制升级。此前报告的漏洞数量需重新扫描，不当作当前已复核结果。
4. C2PA 等原生依赖正常安装路径可复现，不能把忽略全部安装脚本作为最终构建方案；可选功能缺失时有明确的禁用行为。
5. 本地容量基线记录指定硬件、并发、队列等待和接口分位延迟；证明受控退化与背压，不由此推导真实供应商吞吐量。
6. 浏览器截图结合操作断言验证布局和状态；截图本身不等于端到端验收。

## 11. 数据迁移与发布策略

采用“新增兼容结构 → 预检与回填 → 校验 → 按开关切换 → 观察 → 延后清理旧字段”。数据库使用版本化 Prisma migrations，正式数据不使用 db push 代替迁移。

- 先盘点实际用户、订单、流水、任务和上传对象数量，确认是否存在需保留的有效历史数据。
- 金额迁移按订单类型、价格快照和支付来源核对。不能对所有 Float 金额统一乘 100；无法判断单位的记录进入异常清单，禁止自动作为可支配权益发放。
- 对已发生的错误通过有来源的调整流水处理。只有通过核对的数据才能作为新账本开账依据，不修改旧流水制造表面平衡。
- 为旧消费补 sourceTransactionId/cycleId 时，不能仅靠金额和时间猜测；不确定关联需审计和人工处理。
- 将旧上传文件迁入私有对象存储并建立 owner 映射，使用幂等清单核对 checksum。切换后控制旧公开路径，不能为了兼容继续无限期公开用户素材。
- 删除旧用户供应商密钥表和接口；平台供应商密钥继续使用版本化加密并由管理员统一轮换。
- 旧任务执行器与新 Worker 不得同时消费同一任务。切换时停止旧提交，排空或核对处理中任务，再开启新路由；遗留未知任务进入对账。
- 删除素材先标记并检查任务引用，保留期届满再清理原图、衍生图和导出文件。账务与审计按独立保留政策处理，用户删除不能级联抹除需保留的财务记录。
- 回滚优先回退应用开关并保持新增结构兼容。已经发生的新账务业务不能通过回滚数据库快照抹去，应继续对账及补偿。
- 本地用合成数据演练备份恢复、部分迁移重跑和版本回退；真实数据库备份、恢复时间与切换窗口的验证另行验收。

## 12. 可观测性和运维交付

日志统一关联 traceId、userId、jobId、attemptId、orderId，错误有稳定分类。默认不记录密钥、完整提示词、用户原图或带授权参数的 URL。

监控项目包括：队列积压/最老等待时间、Outbox 延迟、租约失效、未知结果数量、供应商失败与限流、生成耗时、实际成本与收费、预留长时间未结算、webhook 未处理事件、导出失败和存储错误。阈值基于本地基线给初值，真实环境后校准；本轮仅模拟触发通知，不冒充真实告警验证。

补充环境变量校验、服务角色最小权限、Key 轮换说明、存活与就绪探针、队列并发/限流/背压、优雅停机和存储清理。数据库或 Redis 不可用时，应可解释地拒绝新提交或保留已入库待调度事件，不能返回虚假成功。

交付运行手册至少覆盖：如何启动 Web/Worker/Dispatcher，如何找一笔消费对应的任务，如何重放支付事件，如何处理未知供应商结果，如何执行幂等补偿，如何恢复数据库和对象引用。

## 14. 第一阶段的具体起点

实施先从 M0 开始，同时把不安全 API Key 登录和未闭环支付入口列为受控禁用项。第一个可演示的业务里程碑应是：使用测试账户上传私有服装素材，获得报价并提交两张图，模拟一张成功、一张失败，刷新和重启后仍能恢复任务，并看到成功项确认消费、失败项释放预留以及完整流水。

该里程碑覆盖 M1/M2 的关键纵向链路。它通过后再扩大到多供应商能力、完整支付和前端细节，可以让后续每项功能都有稳定的身份、资产、任务和账务基础。

每阶段结束提交一份实际开发记录：完成内容、数据/API 变化、测试结果、已知限制和下一阶段依赖。本方案本身不表示这些工作已经实施。
