# 画布自动保存故障处理

## 本次确认的事实

- 用户截图的失败接口是 `POST /api/studio/documents`，并不是生成任务接口。
- 原来的 `REQUEST_FAILED` 表示非成功 HTTP 响应没有提供应用错误码；原 UI 没有显示 HTTP 状态。仅凭截图无法区分网关 413、502、503、504 等原因。本次没有读取生产服务器日志，不能将某一种原因认定为线上根因。
- 画布原有队列已经串行提交，但临时失败后没有重试。已提交、响应丢失的更新再次提交会产生版本冲突。
- 图层保存的是素材 ID 和几何参数，不是整张图片的 Base64。没有证据表明截图中的十张图直接导致请求超过限制。

## 修改后的行为

1. 每个保存快照使用独立的 `saveKey`，服务器保存最近一次 key 和规范化请求的 SHA-256。相同请求重试不重复增加版本；同 key 不同内容、其他标签页的新版本仍被拒绝。
2. 连接异常、超时、408/429/500/502/503/504 和损坏的成功响应最多请求三次，间隔 750 ms、2000 ms，单次请求超时 20 秒。权限、校验、413 和版本冲突不自动重试。此策略仅用于画布保存，不重试付费生图请求。
3. 未确认请求随草稿写入 IndexedDB；之后保存先确认这个请求，再提交新的修改。刷新时也能凭保存标识确认自己的已提交版本，不误判为他人的修改。
4. 短暂故障显示“正在重试保存”，恢复成功不弹报错。重试耗尽后明确提示云端尚未同步；HTTP 状态码及应用 trace ID 可用于排查。切换项目/账户后不继续重试旧请求。
5. 保存事务显式设置连接等待 10 秒、事务执行 15 秒，给短暂数据库排队留出余量；这不代表已确认线上根因是数据库超时。
6. 服务日志记录 `studio.document.save.failed`、trace ID、耗时、状态、异常类型和 Prisma 错误码，不记录提示词、图片内容或密钥。

## 部署

本次包含可向后兼容的迁移 `202610180002_document_save_receipt`，增加两个 nullable 字段。新 Web 启动前必须执行正式迁移。仓库现有 `sh scripts/deploy-update.sh` 已包含拉取镜像、迁移、更新 Web/Worker 的顺序；代码部署使用 `npm run db:migrate` 后再启动新构建。

## 如果线上仍失败

按页面显示的 HTTP 状态和 trace ID 对照 Web 日志。413 检查反代请求体限制（应用文档接口上限 4 MiB）；502/503/504 对照网关日志、Web 容器重启/OOM 和数据库连接情况。网关直接返回的错误可能没有应用 trace ID，此时按请求时间及接口定位。不要通过清空用户缓存处理保存故障，缓存中可能还有未同步修改。

## 回归覆盖

- 传输：HTML 502、持续 503、网络断开、损坏的成功响应、永久失败不重试、项目切换停止重试。
- 草稿：保存中继续编辑、未确认写入再次保存、刷新后识别已提交版本、真实版本冲突保留本地内容。
- 数据库：创建和更新的幂等性、请求 key 内容校验、用户隔离及多页面版本冲突。
- 浏览器：真实保存已提交后模拟 502，同时继续编辑，检查最新内容、最终版本、草稿同步标记和刷新后的内容。
